# AI下半场，程序员如何与AI协作

> 写作状态：采访素材已整理，以下为文章骨架，正文待展开。

## 暂定核心命题

**AI 是放大器。Code Agent 擅长在明确边界内做局部优化，却不擅长处理全局架构、代码质量、长期演化和未来规划。程序员的核心价值，正在从“实现者”转向目标定义者、上下文组织者、质量验证者和最终兜底者。**

## 文章结构

1. **引言：AI 提效是真的，焦虑叙事也是真的**
   - 从个人转向经历切入：2023 年开始使用大模型，逐渐从辅助理解代码走向让 Agent 承担主要研发工作。
   - 提出反差：生产能力显著提升，但团队和个人的成长感并没有同步提升。
   - 点出文章立场：不必恐慌，也不能盲信；真正需要改变的是协作方式和责任边界。

2. **这几年，我和 Code Agent 的协作发生了什么变化**
   - 2023 年开始接触大模型；今年春节后，Code Agent 开始进入主要研发流程。
   - Claude Sonnet 4.6 之后，模型第一次让人感到可以处理大型项目，而不只是生成脚本和局部代码。
   - 典型成功案例：没有 TypeScript 和 Terminal 开发经验，仍完成了 AI 知识生成项目。
   - 辅助案例：复用已有项目的经验和模式，约 1 周开发爬虫 skill，约 2 周打磨知识生成 Terminal App。
   - 这一段回答：AI 提效为什么是事实。

3. **Agent 能做什么，不能做什么**
   - Agent 擅长局部修复、模式复用、代码生成、测试补全和明确任务的快速闭环。
   - Agent 不擅长跨模块影响评估、全局架构、系统性重构、长期技术债权衡和性能问题定位。
   - 原因一：当前主流训练模式更擅长确定性任务和可验证奖励，代码质量和全局架构的 rubric 很难定义。
   - 原因二：性能问题等真实环境缺陷难以稳定复现，也就难以形成有效训练数据。
   - 原因三：所谓自进化仍以规则、经验文本和 harness 为主，短期难以真正内化进模型。
   - 结论：模型能力不是无限变量，工程能力和产品能力才是当前更大的变量。

4. **成功模式：把 Agent 放在可验证的工程闭环里**
   - 先调研业界方案和相似项目，再给 Agent 足够的上下文参考。
   - 用 OpenSpec、Superpowers、SpecKit 等研发 skill 约束过程。
   - 采用 TDD 和模块化，把复杂工作变成可以验证的小任务。
   - 提前打磨部署验证 skill，让后续开发可以自动验证。
   - 这一段回答：为什么有些项目可以做得又快又稳。

5. **失败模式：多人 vibe coding 会放大混乱**
   - 项目背景：RAG 项目，4 至 5 名常驻研发，另有约 5 人不定时提交代码。
   - 个人职责：负责 RAG 数据解析、内容质量，以及项目主要推进。
   - 问题一：目标本身没有想清楚，Agent 只能加速错误方向的执行。
   - 问题二：多人协作缺少统一边界和验收标准，代码不断堆叠。
   - 具体症状：应用层数据库操作缺少事务、连接泄漏、大量使用 Redis 保存业务数据。
   - 结果：项目快速上线，但缺陷频发，甚至影响其他系统；团队需要返工和假期加班修复。
   - 这一段回答：为什么“更快写代码”不等于“更快交付价值”。

6. **返工之后，我改变了几件事**
   - 清理上下文：消除歧义、冗余和低质量代码，给 Agent 一个更干净的输入环境。
   - 文档与代码同步：参考 DeepSeek harness 的文档化方式，记录功能意图、说明和变更原因。
   - Plan 先给人读：计划要精简，尽早描述重点变更、影响和原因，并用流程图表达过程。
   - 多 Agent 审查：使用多个 review agent 检查不同维度，但最终判断仍由人完成。
   - 人类保留区域：系统优化、跨模块重构、技术方向、产品取舍和最终责任。
   - 这一段回答：如何把教训转化为可执行的协作方法。

7. **不同角色应该怎么做**
   - 初级程序员：用 Agent 加快学习，但必须能解释、修改和验证它的输出；模型会不等于自己会。
   - 资深工程师：把精力转向架构约束、质量闸门、验证基础设施和复杂问题判断。
   - 技术管理者：不要把生成速度误认为交付能力；投资代码健康、文档同步、验收机制和风险边界。
   - 共同原则：模型是放大器，先有自己的判断，再让 Agent 放大判断。

8. **结语：不要被速度带走**
   - 当前 AI 的改变是真实的，但资本叙事把变化描述成了不可抗拒的替代。
   - Agent 是高速的局部优化器，人仍然要承担全局规划和长期责任。
   - 真正需要训练的，不是更花哨的 Prompt，而是问题定义、工程判断、产品理解和持续学习能力。
